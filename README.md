# Inventory & Dispensing Management System

Pharma-grade inventory tracking: product catalog, per-location stock with
concurrency-safe dispensing, RBAC across Admin/Employee/Customer panels, and
real-time low-stock alerts.

Full architecture, database schema, and the phase-by-phase build plan live in
**[`docs/architecture.md`](./docs/architecture.md)** — read that first.

## Repo layout
```
apps/
  api/    NestJS backend (REST + WebSocket gateway, Prisma/PostgreSQL, Redis)
  web/    React + Vite frontend — one app, three route groups: /admin /staff /shop
packages/
  shared-types/   Types/DTOs shared between api and web
docs/
  architecture.md   Full design doc + roadmap
```

## Status
**Phase 0 — Foundations: done.** Both apps scaffolded, Docker Compose for Postgres/Redis, CI skeleton.

**Phase 1 — Auth & RBAC core: done.**
- **Schema**: `User`, `Role`, `Permission`, `UserRole`, `RolePermission`, `RefreshToken` (see `apps/api/prisma/schema.prisma`).
- **Auth flow**: `POST /api/auth/login` (email+password → argon2 verify → access JWT + refresh cookie), `POST /api/auth/refresh` (rotates the refresh token, detects reuse and revokes the whole session family if a used token is replayed), `POST /api/auth/logout`.
- **Token handling**: short-lived signed JWT access token returned in the response body only (frontend keeps it in memory, never localStorage); long-lived opaque refresh token in an `httpOnly`, `sameSite=lax` cookie scoped to `/api/auth`, stored server-side as a hash.
- **RBAC**: permission codes (`product:view`, `stock:adjust`, `dispense:create`, …) assigned to roles (`Admin`/`Employee`/`Customer`), cached in Redis per role with a 5-minute TTL. `@RequirePermissions('code')` on any controller method enforces it via a global guard; `@Public()` opts a route out of auth entirely (login/refresh/logout/health).
- **Global guard chain**: rate limiting → JWT auth (unless `@Public()`) → permission check (unless no `@RequirePermissions()`).
- **Endpoints**: `GET /api/users/me`, `GET/POST /api/users` (admin), `GET /api/roles` (admin) — see `apps/api/src/{users,roles}`.
- **Seed script**: `npm run seed --workspace=api` creates all permissions, the three default roles, and a bootstrap Admin user (`SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`, defaults in `.env.example`).
- **Frontend**: `AuthContext` (silent refresh on load, in-memory access token, axios interceptor that retries once through `/auth/refresh` on a 401), a login page, and `ProtectedRoute` that redirects unauthenticated users to `/login` and authenticated-but-wrong-role users to their own panel.

**Phase 2 — Catalog: done.**
- **Schema**: `Brand`, `Category` (self-referencing parent/children), `Location` (self-referencing parent/children, e.g. warehouse → aisle → shelf), `Product` (references brand + category, `Restrict` on delete so a brand/category in use can't be removed out from under a product).
- **API**: full CRUD for all four (`/api/brands`, `/api/categories`, `/api/locations`, `/api/products`), plus `GET /categories/tree` and `GET /locations/tree` for nested picker UIs, and `GET /products/sku/:skuCode` for barcode-style lookup. Reads are gated by `product:view` (already held by every seeded role); writes by `brand:manage`/`category:manage`/`location:manage`/`product:create`/`product:update`. Deactivating a product is a separate `PATCH /products/:id/status` gated by `product:delete` — there's no real DELETE for products, only soft-delete via `isActive`, since Phase 4's usage_logs will make hard deletes impossible anyway once a product has history.
- **Data integrity**: category/location parent assignment is checked server-side for cycles (walks the ancestor chain, not just a same-id check) — see `categories.service.spec.ts` for the test proving it. Prisma constraint violations (duplicate SKU, deleting a brand still referenced by products, etc.) are translated into clean 409/404 responses instead of leaking raw DB errors (`common/prisma-error.util.ts`).
- **Frontend**: an actual Admin shell (`AdminLayout`, sidebar nav) replacing the Phase 1 placeholder, with full pages for Brands, Categories, and Locations (create/rename/delete, parent picker), and a Products page with search, brand/category/status filters, pagination, create/edit, and the activate/deactivate toggle.

**Phase 3 — Stock management: done.**
- **Schema**: `InventoryStock` (per product+location+batch, `quantity`/`thresholdLimit`, unique on the triple) and `StockAdjustment` (immutable audit trail — no update/delete endpoint exists for it at all).
- **The zero-negative-stock guarantee**: Prisma's schema DSL still has no stable declarative `CHECK` constraint syntax, so instead of a DB constraint, `InventoryService.adjust()` uses an atomic conditional `UPDATE ... SET quantity = quantity + $delta WHERE quantity + $delta >= 0` — a single statement that checks and applies the change together, so no concurrent adjustment can race it into negative. See the comment on `InventoryStock` in `schema.prisma` for the exact SQL to add a belt-and-suspenders DB constraint too, once you have a migration history to hang it off of. This is the same pattern Phase 4's dispensing engine will build on with `SELECT ... FOR UPDATE`.
- **API**: `GET /api/inventory` (filter by product/location/low-stock-only, paginated), `POST /api/inventory` (explicit stock-row creation), `PATCH /api/inventory/:id/threshold`, `POST /api/inventory/adjustments` (the core restock/correction/damage/expired action — get-or-creates the stock row, applies the change atomically, writes the audit record, all in one transaction), `GET /api/inventory/:id/adjustments` (history). Reads need `stock:view`; writes need `stock:adjust` — both Admin-only in the seed, matching the architecture doc's separation of duties (Employees dispense in Phase 4, they don't restock).
- **Tested, not just written**: `inventory.service.spec.ts` mocks the transaction client and actually proves the negative-stock rejection, the sign-matches-adjustment-type validation, and both branches of the get-or-create race handling — 8 tests, all passing.
- **Frontend**: a Stock page (`/admin/stock`) with product/location/low-stock filters, a restock/correction form, inline threshold editing, and an expandable per-row adjustment history.

**Phase 4 — Dispensing engine: done.**
- **Schema**: `UsageLog` — insert-only (no update/delete endpoint at all), `Int` id rather than the `BigInt` the original architecture draft suggested (BigInt serializes to JS `bigint`, which `JSON.stringify` throws on without a custom replacer; Int's ~2.1 billion ceiling isn't a real constraint here — see the comment on the model).
- **The actual "zero negative stock" proof**: `DispenseService.dispense()` uses real pessimistic locking — `SELECT ... FOR UPDATE` inside a transaction — rather than Phase 3's atomic-conditional-UPDATE approach. This is deliberate: it's the mechanism docs/architecture.md §4.2 calls out specifically for the highest-contention path (two employees dispensing the last unit at once), and Phase 3 already demonstrated the other technique, so between the two phases both patterns from the architecture doc are implemented and tested, not just described.
- **API**: `POST /api/dispense` (the locked transaction — checks stock under the row lock, decrements, writes the usage log, all atomically), `GET /api/dispense` (filterable, paginated history), `GET /api/dispense/:id`. `dispense:create` and `dispense:view` were already Employee-held permissions from the Phase 1 seed — no seed changes needed, and Employees still can't restock (`stock:adjust` stays Admin-only), matching the architecture doc's separation-of-duties intent.
- **Two levels of proof, not one**: `dispense.service.spec.ts` mocks the transaction client and covers the insufficient-stock rejection, the missing-stock-row case, and the boundary of dispensing exactly what's left (6 tests). But a mock can't prove a *real* row lock actually serializes concurrent transactions — only Postgres can. `test/dispense-concurrency.e2e-spec.ts` is the real proof: it seeds exactly 1 unit of stock, fires two dispense requests with `Promise.all` (no await between them), and asserts exactly one returns 201 and the other 400 — never both succeeding, never a negative quantity afterward. This needs a live Postgres, so it couldn't run in this sandbox; run it yourself with `npm run test:e2e` once your local DB is up and seeded (see below).
- **Frontend**: the Employee panel (`/staff`) is now a real dispensing UI — SKU/barcode-style lookup, product/location/quantity/purpose form, live insufficient-stock error surfacing, and a recent-activity feed.

**Phase 5 — Real-time alerts: done.**
- **Schema**: `AlertLog` — a durable record of every threshold breach, independent of whether anyone was online to see the WebSocket push at the time (so the Admin panel can always show what's still unacknowledged, not just what happened to be seen live).
- **Crossing-based, not literal-doc-reading**: `AlertsService.maybeTriggerLowStockAlert()` only fires when stock goes from *above* threshold to *at-or-below* it — not on every single action while a product sits low. The architecture doc's literal §6.2 lifecycle re-evaluates on every change, which would mean a new toast and a new `AlertLog` row for every dispense while something stays low; crossing-only is a deliberate improvement documented right in the code, not a missed requirement.
- **Redis Pub/Sub fan-out**: `RedisService` now runs two connections — the existing general-purpose one (used for permission caching, and for `PUBLISH`, which is a normal command) plus a dedicated `subscriber` connection, because Redis puts a connection that's issued `SUBSCRIBE` into a restricted mode that can't run ordinary commands anymore. `AlertsGateway` subscribes to `inventory:low_stock_alerts` once per server instance on boot, so the fan-out pattern in docs/architecture.md §6.2 holds even across multiple horizontally-scaled nodes.
- **WebSocket auth**: Socket.io connections don't go through Nest's HTTP Guard pipeline, so `AlertsGateway.handleConnection()` verifies the JWT and checks for `stock:view` by hand, once, at handshake time — the same two-step REST requests get automatically. A connection without a valid token or without that permission is rejected outright.
- **API**: `GET /api/alerts` (history, filterable by acknowledged/open), `PATCH /api/alerts/:id/acknowledge`. Both reuse `stock:view` rather than adding a new permission code — Employee and Admin both already hold it from the Phase 1 seed, matching who the WebSocket gateway lets connect in the first place.
- **Wired into the two places stock actually changes**: both `InventoryService.adjust()` (Phase 3) and `DispenseService.dispense()` (Phase 4) now call the alert check right after their transaction commits — deliberately *after*, not inside, so a Redis or alert-table hiccup can never block a restock or a dispense that already succeeded. 12 new tests across `alerts.service.spec.ts`, `inventory.service.spec.ts`, and `dispense.service.spec.ts` cover the crossing logic, the resilience guarantee (alerting failures never propagate), and that the *pre*-decrement quantity is what gets checked.
- **Frontend**: `AlertsContext` connects the socket only for roles that can actually receive alerts (Admin/Employee — Customer accounts would just get rejected by the gateway anyway), a toast queue with auto-dismiss rendered globally across every panel, and an Admin Alerts page (`/admin/alerts`) with acknowledge and an open/all filter.

**Phase 6 — Customer panel: done.**
- **Schema**: `ProductReview` — one review per (product, customer) pair enforced by a unique constraint (not in the original architecture.md draft, added deliberately so a customer can't flood a product's rating; resubmitting updates their existing review instead of erroring, see below).
- **Public self-registration**: `POST /api/auth/register` — the one new genuinely-unauthenticated write endpoint in the whole system. It hardcodes the `Customer` role server-side; `RegisterDto` doesn't even have a role field, so there's no privilege-escalation path from a public signup form to Admin. Tested by actually trying to smuggle a role through and confirming it's ignored, not just assumed safe.
- **Public catalog browsing**: `GET` on products/brands/categories switched from `product:view`-gated to `@Public()` — genuine storefront browsing, no account required, matching the architecture doc's framing of the Customer panel as "public-facing." Verified this doesn't regress Admin/Employee usage: `@Public()` just skips populating `request.user`, it doesn't reject a valid token that's still sent.
- **Redis-cached catalog reads**: `ProductsService` now does cache-aside reads with a version-counter invalidation scheme (every write bumps a counter rather than trying to enumerate and delete keys — no `SCAN`/`KEYS` in production Redis) — the specific caching the architecture doc calls out in §7.3 for the customer storefront. Cache failures degrade to a normal DB read rather than a failed request, same resilience posture as the alerting system.
- **Reviews with a real moderation gate**: `POST /api/reviews` (auth required, `review:create`) always lands as `status: 'pending'`. The public `GET /api/reviews` endpoint hardcodes `status: 'approved'` server-side — there's no query parameter that reaches a pending or rejected review through it. A separate `GET /api/reviews/moderation` (permission-gated, `review:moderate`) is the only place those become visible, with `PATCH /api/reviews/:id/moderate` to approve/reject.
- **Tested, including the gate itself**: 9 new tests (5 for the review upsert/status-hardcoding logic, 3 for registration's role-hardcoding, 1 new e2e flow) — **37 unit tests passing**, plus a new `test/customer-flow.e2e-spec.ts` that proves the real end-to-end story: anonymous browsing works with zero auth headers, a freshly-registered customer gets a 403 (not 401 — they *are* authenticated) from an Admin-only route, and a submitted review is invisible on the public listing until an Admin approves it. Same sandbox limitation as the Phase 4 concurrency test: written and lint-checked, never actually run here — no live Postgres in this sandbox.
- **Frontend**: `/shop` is now a real public storefront (`ShopLayout`, product grid, product detail with reviews) reachable with zero login, a `/register` page, and an Admin review moderation queue (`/admin/reviews`). The root `/` route now sends anonymous visitors to `/shop` instead of a login wall — only the Admin/Employee panels still gate on auth up front.

**Phase 7 — Product details aggregation & reporting: done.**
- **Schema**: `AuditLog` — a general-purpose admin/security trail distinct from `usage_logs` (dispensing) and `stock_adjustments` (restocking), which are already domain-specific audit trails in their own right. `SetNull` on the actor FK, same precedent as `AlertLog.acknowledgedBy`: losing track of exactly who performed a long-past action isn't worth blocking user deletion over.
- **Deliberately scoped, not exhaustive**: `AuditLogService.record()` is wired into five real actions — user creation, product activate/deactivate, review moderation, and brand/category/location deletion — not every mutation in the system. Instrumenting everything would bury the actually-meaningful entries in noise; this is a judgment call stated outright in the code, not a gap I'm hoping goes unnoticed. Same resilience posture as Phase 5's alerting: `record()` never throws, so a hiccup in the audit table can never be the reason an Admin action itself fails.
- **The real Product Details Aggregation** (`GET /api/products/:id/details`) — architecture.md §7.4's four-part sequence (metadata, live stock, usage aggregation, chronological ledger) plus a stock-adjustment history and review summary the original draft didn't call out but which round out the same "holistic profile" goal. Deliberately **not** cached like the public product reads — this is a low-traffic internal view that exists specifically so staff can trust the numbers are current; caching it would undermine the point.
- **A real TS inference bug caught and fixed, not just Prisma-stub noise**: building `ReportsService` hit a genuine `TS2339` error unrelated to the sandbox's broken Prisma client — `new Map()` constructed from an untyped array wasn't propagating `any` cleanly through TypeScript's inference in this specific case. Fixed with an explicit shape annotation rather than papering over it; documented inline so it doesn't look like copy-paste cruft.
- **Reports + CSV export**: `GET /api/reports/usage-summary` (times dispensed + total quantity per product, optional date range, sorted by volume), `GET /api/reports/usage-summary/export` for the same data as a real file download (`Content-Disposition: attachment`). The CSV serializer (`common/csv.util.ts`) is hand-rolled rather than a dependency — small enough to own directly, and it's unit-tested against the actual RFC 4180 edge cases (embedded commas, quotes, newlines), not just the happy path.
- **Tested**: 10 new tests (CSV quoting edge cases, the report's product-join and date-range logic including a "product no longer resolves" fallback, and `AuditLogService`'s never-throws guarantee) — **47 unit tests passing**. Two new e2e specs (`test/audit-and-reports.e2e-spec.ts` proving an audit entry is actually queryable after a real action, not just written) join the same "written and lint-checked, never run here" list as the earlier ones — no live Postgres in this sandbox.
- **Frontend**: an Admin product detail page (`/admin/products/:id`, linked from the Products table) showing the full aggregation, an Audit Log view (`/admin/audit-log`) with action/entity filters, and a Reports page (`/admin/reports`) with a date range and a working CSV download button.

**Phase 8 — Hardening & deployment: done. This completes the roadmap in `docs/architecture.md`.**
- **A bug this phase's own testing caught, not just Prisma-stub noise**: the API Dockerfile's `CMD` pointed at `dist/main.js`, but the actual compiled entry (given `nest-cli.json`'s `sourceRoot: "src"`) is `dist/src/main.js` — confirmed by actually compiling and inspecting `dist/`, not assumed. Both Dockerfiles also had a deeper issue: this is an npm **workspaces monorepo**, and a Docker build context scoped to `apps/api`/`apps/web` alone can't resolve the root lockfile correctly. Both are rewritten to build from the repo root, documented at the top of each Dockerfile and in `DEPLOYMENT.md` §3.
- **Structured logging** via `nestjs-pino` (`common/logger.config.ts`) — every request is one JSON log line in production (pretty-printed in dev), with the `Authorization` header, refresh-token cookie, and request-body `password`/`newPassword` fields redacted before they're ever serialized. That redaction is the part that actually matters: without it, every login request would log the password in plaintext.
- **A global exception filter** (`AllExceptionsFilter`) — every error, `HttpException` or not, now returns a consistent JSON shape with no stack trace leaked to the client, logged at `error` level if it's a genuine 5xx/unexpected failure or `debug` if it's normal 4xx traffic (a 404 isn't an incident).
- **Tighter throttling on the two unauthenticated write endpoints** — `login` and `register` (5/min, down from the global 100/min default), `refresh` at 20/min since the frontend calls it automatically. Verified for real, not just written: the bootstrap test below actually checks the `x-ratelimit-limit` response header reflects `5`, not the global default.
- **A real liveness/readiness split** — `GET /api/health` (liveness, no dependency checks — a slow DB should never cause a restart loop) and `GET /api/health/ready` (checks Postgres + Redis, returns 503 with a per-dependency breakdown if either is down).
- **A test that can verify something the others structurally can't**: every other integration-style test in this repo needs a live Postgres/Redis and couldn't run in this sandbox. `src/app.module.spec.ts` mocks only `PrismaService`/`RedisService` at the DI level and boots the **entire real module graph** — all 21 feature modules, every guard, the new `LoggerModule` and `AllExceptionsFilter` — which is the only way to catch a circular-dependency or provider-resolution bug before someone actually runs the app for the first time. It genuinely runs here (**52 unit tests passing**, no live database needed for this one), and it's what caught the readiness endpoint correctly degrading to a 503 instead of crashing when a dependency is unreachable.
- **A complete CI workflow** — the migration/test steps that were commented out since Phase 0 (because they didn't exist yet) are now real: install → `prisma generate` → lint → build → `prisma migrate deploy` → seed → unit tests → e2e tests, against real Postgres/Redis service containers. This is the one place in the whole project where the Prisma-stub limitation fully resolves — a GitHub Actions runner has normal internet access, so it reaches Prisma's engine CDN and every `no-unsafe-*` warning documented throughout this README clears there.
- **`DEPLOYMENT.md`** — environment variables, migration strategy (`migrate deploy`, never `migrate dev`, in production), Docker build instructions, reverse proxy/TLS and WebSocket-upgrade requirements, the liveness/readiness distinction, log redaction, backup/restore commands with the caveat that an untested restore isn't a backup, and why horizontal scaling already works without extra configuration (the Phase 5 Redis Pub/Sub design was specifically for this).

### Trying it locally
```bash
npm install
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env
npm run dev:infra                 # Postgres + Redis
cd apps/api && npx prisma generate && npx prisma migrate dev --name init
npm run seed --workspace=api      # creates roles/permissions + admin@example.com
cd ../.. && npm run dev:api       # terminal 1
npm run dev:web                   # terminal 2
```
Then open http://localhost:5173 — you land on `/shop` immediately, no login needed, and can browse whatever catalog data exists. Sign in as `admin@example.com` / the password from `SEED_ADMIN_PASSWORD` (defaults to `ChangeMe123!` if unset) to reach `/admin`. Add a brand, category, location, and product, restock it from `/admin/stock` with a small quantity right above its threshold, then either dispense it yourself from `/staff` (you'll need to also hold the Employee role — the seed only grants Admin — or create a second user with `POST /api/users` and the Employee role) or just run the real concurrency proof directly:
```bash
cd apps/api && npm run test:e2e
```
To see a live alert: restock a product to, say, 6 units with its threshold at 5, then dispense 2 — the toast should appear in the browser within a second, with no page refresh, and it'll show up in `/admin/alerts` whether or not you were watching when it fired. Click into any product from `/admin/products` to see its full aggregated profile, check `/admin/audit-log` after deactivating a product or moderating a review, and try `/admin/reports` for a CSV you can open in a spreadsheet.

For production deployment, read **`DEPLOYMENT.md`** before doing anything else — it covers the environment variables, migration strategy, Docker build (the context has to be the repo root, not `apps/api`/`apps/web`), reverse proxy/TLS requirements, and backup procedure.

To try the customer flow: open `/register` in an incognito window (or log out first), create an account, browse to a product, and submit a review — it won't show up on that product page until you approve it from `/admin/reviews` in your admin session.

> This scaffold was built in a network-sandboxed environment where Prisma's engine-binary CDN wasn't reachable, so `prisma generate`/`migrate` couldn't be run there and the Prisma client shipped as an untyped stub — you'll see `@typescript-eslint/no-unsafe-*` lint warnings in every file that calls `this.prisma.*` directly (auth, users, roles, and every catalog/stock/dispense/alerts/reviews/audit-log/reports service) until you run `npx prisma generate` for real, which produces fully-typed models and clears them automatically (no code changes needed) — one genuine, non-Prisma-stub TypeScript inference bug was hit and fixed along the way in `reports.service.ts`, noted inline. The same sandbox also had no Postgres/Redis available at all, so `test/app.e2e-spec.ts`, `test/dispense-concurrency.e2e-spec.ts`, `test/customer-flow.e2e-spec.ts`, and `test/audit-and-reports.e2e-spec.ts` were written and lint-checked but never actually run — they need `npm run test:e2e` against your local, seeded database to execute for the first time. The Phase 5 WebSocket gateway and Redis Pub/Sub fan-out are in the same boat: the crossing-detection logic is genuinely unit-tested with a mocked Redis client, but the actual socket handshake, JWT verification over a live connection, and cross-instance Pub/Sub delivery have only been read-through, never run end-to-end — that first real verification happens when you open the app in a browser against your local stack.
